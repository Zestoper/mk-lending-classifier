# MK Lending 대출서류 분류기

여러 종류의 대출 서류가 무작위로 섞인 PDF 패키지를 입력받아, 페이지 단위로
문서 유형을 분류하고(URLA_1003 / CREDIT_REPORT / TITLE_REPORT / INCOME_DOC /
OTHER), 연속된 페이지를 하나의 문서로 그룹핑하는 프로젝트입니다.

## 1. 문제 정의 및 접근 순서

문제를 다음 순서로 쪼개서 접근했습니다.

1. **먼저 실제 데이터를 눈으로 본다.** 정규식을 짜기 전에 `extract.py`로
   PDF 39페이지 텍스트를 뽑아 직접 읽으며 카테고리별 반복 패턴을 찾았습니다.
2. **정답(GT) 없이는 아무것도 검증할 수 없다.** `package_01_gt.json`이
   제공되지 않아, 함께 제공된 섞이기 전 원본 4개 문서(URLA/Credit
   Report/Income P&L/Title Report)와 shuffled 페이지를 텍스트 유사도로
   대조해 GT를 직접 역산했습니다.
3. **규칙(정규식)만으로 얼마나 되는지 먼저 측정한다.** LLM 없이 순수
   키워드 매칭으로 베이스라인을 잡았습니다.
4. **규칙이 실패하는 지점만 정밀하게 LLM으로 보완한다.** 전체를 LLM에
   맡기지 않고, 규칙이 못 잡는 페이지만 골라서 넘겼습니다.
5. **분류 결과를 문서 단위로 그룹핑한다.**
6. **정확도/오답을 측정하고 한계를 정리한다.**

이 순서를 택한 이유는, 규칙 기반부터 시작해야 "LLM이 왜 필요한지"를
데이터로 증명할 수 있고, 반대로 LLM부터 시작하면 규칙으로 충분한 페이지까지
불필요하게 API를 호출하게 되기 때문입니다.

## 2. 기술 스택 선택과 근거

### 2.1 텍스트 추출: pdfplumber

별도 OCR 없이 텍스트 레이어가 있는 PDF였음을 확인(`char_count=0`인 페이지
0개)하고 `pdfplumber`만으로 진행했습니다. 스캔 이미지 위주 PDF였다면 OCR이
추가로 필요했을 것입니다.

**발견한 문제와 원인 규명 과정**: 일부 페이지에서 텍스트 전체가 문자
단위로 반전되어 추출되는 현상을 발견했습니다
(`"MK LENDING CORP"` → `"PROC GNIDNEL KM"`). 처음엔 PDF 병합(shuffle)
과정에서 생긴 텍스트 인코딩 버그로 추정하고, 흔한 영어 단어 매칭 개수를
정방향/역방향으로 비교하는 휴리스틱으로 감지·복원했습니다.

이후 분류 결과를 실제 PDF 파일로 쪼개서 눈으로 확인하는 과정(`pypdf`로
페이지 복사)에서, 복사된 페이지가 화면에 옆으로/거꾸로 돌아간 채로
보이는 것을 발견했고, `pypdf`로 `/Rotate` 메타데이터를 직접 확인해
**진짜 원인이 텍스트 인코딩 문제가 아니라 페이지 자체의 회전
(90/180/270도)** 이었다는 것을 특정했습니다. package_01 39페이지 중
26페이지에 `/Rotate`가 걸려있었고(0도 13페이지, 90도 9페이지, 180도
10페이지, 270도 7페이지), 섞이기 전 원본 개별 문서에는 이 회전이
전혀 없었던 것으로 확인되어 병합(shuffle) 과정에서 생긴 것으로
추정했습니다.

- `/Rotate=180`(및 이 문서에서는 270도 페이지 대부분)에서는 `pdfplumber`가
  텍스트를 정확히 문자 단위로 뒤집어서 반환했습니다 — 이 경우
  `text[::-1]`이 수학적으로도 타당한 복원 방법입니다.
- `/Rotate=90`에서는 반전이 아니라 단어 단위 읽기 순서만 뒤섞였습니다
  (단어 철자 자체는 정상). 이 경우는 정규식 키워드 매칭이 단어 순서에
  영향받지 않으므로 별도 처리 없이도 규칙 기반 분류가 정상 동작했습니다.
- 감지 방법(휴리스틱): 흔한 영어 단어(the, and, report, page 등, 3글자
  이상만 사용)가 원문 방향과 뒤집은 방향 중 어느 쪽에 더 많이 매칭되는지
  비교. 짧은 단어(on/or/is 등)는 반전된 다른 단어와 우연히 같은 철자가
  되는 오탐이 있어 제외했고, 근소한 차이(margin=2 미만)는 반전으로
  확정하지 않도록 했습니다. `/Rotate` 값을 직접 읽어 180도인 페이지만
  결정적으로 복원하는 방식이 이 휴리스틱보다 더 정확했겠지만, 이미
  검증된 휴리스틱이 결과적으로 180도 페이지를 전부 정확히 잡아내고
  있어(실제 겹치는 것을 확인) 그대로 유지했습니다.
- **왜 정규식 패턴을 정방향/역방향 두 벌 만드는 대신 추출 단계에서
  고쳤는가**: 새 키워드를 추가할 때마다 반전 버전도 같이 관리해야 해서
  유지보수 부담이 두 배가 됩니다. 추출 단계에서 한 번 정규화해두면
  이후 모든 단계(규칙, LLM)가 깨끗한 텍스트를 받습니다.
- **한계**: `/Rotate=270`인 page 8은 회전과 별개로 글자가 이중으로
  겹쳐 찍히는(bold 렌더링 아티팩트) 문제가 함께 있어 `text[::-1]`로도
  복원이 불가능했습니다 (`"sample"`이 `"ssaammppllee"`처럼 나옴). 이
  페이지는 결국 규칙과 LLM 모두 실패했습니다. 반면 사람이 보는 최종
  산출물(쪼갠 PDF 파일)에서는 `pypdf`의 `page.rotate()`로 `/Rotate`를
  0도로 정규화해서 최소한 시각적으로는 똑바로 보이도록 처리했습니다
  (`split_by_category.py`).

### 2.2 1차 분류: 규칙(정규식) 기반

카테고리별로 반복 등장하는 고유 문구를 정규식으로 등록했습니다
(`config.py`). 예: `CREDIT_REPORT` → `ECOA`, `Trended Data`, `XACTUS` 등,
`URLA_1003` → `Uniform Residential Loan Application`, `Fannie Mae Form 1003`
등.

**왜 규칙을 먼저 뒀는가**: 이 문서들은 표준 양식이라 특정 문구가 페이지마다
매우 규칙적으로 반복됩니다. 이런 경우 정규식이 LLM보다 빠르고, 무료이고,
결과가 결정적(deterministic)입니다. package_01 기준 순수 규칙만으로
38/39(97.4%) 정확도가 나왔습니다.

### 2.3 2차 분류: LLM 폴백 (Groq → Cerebras)

규칙이 하나도 매칭하지 못한(match_count=0) 페이지만 LLM으로 재분류합니다.
Groq를 1순위로 호출하고, 예외(rate limit 등) 발생 시 Cerebras로 폴백합니다.

**LLM 호출 기준을 튜닝한 과정**: 처음엔 "매칭 개수 1개 이하"를 저확신
기준으로 잡았으나, 검증 중 `XACTUS`(신용조회 대행사 고유명사) 단 1개
매칭으로 정확히 맞히고 있던 페이지(package_01 3번)까지 LLM으로 넘어가면서
LLM이 오히려 틀리게 뒤집는 역효과를 확인했습니다 (하이브리드 정확도가
94.9%로 규칙 단독 97.4%보다 낮아짐). "매칭 개수가 적다"와 "매칭이 특이적이지
않고 애매하다"는 다른 개념이라는 것을 발견하고, 기준을 "매칭 개수 0개(=규칙이
정말 아무 단서도 못 찾은 경우)"로 좁혔습니다. 그 결과 package_01은 LLM이
정확히 1페이지(반전+중복 아티팩트로 이미 복구 불가능했던 8번)만 호출되었고,
정확도는 규칙 단독과 동일한 97.4%를 유지했습니다.

**왜 처음부터 LLM으로만 풀지 않았는가**: 표준 양식 문서 분류에 매 페이지마다
LLM을 호출하는 것은 비용/속도 면에서 비효율적이고, 재현성도 규칙보다
떨어집니다(같은 입력에도 결과가 흔들릴 수 있음). 반대로 규칙만 쓰면
데이터가 조금만 달라져도(다른 대출 건, 다른 서식) 매칭이 깨질 수 있어
일반화가 어렵습니다. 두 방식의 장점만 취하기 위해 하이브리드로
설계했습니다.

### 2.4 그룹핑

분류 결과를 페이지 번호 순으로 정렬한 뒤, 카테고리가 같고 페이지 번호가
연속인 것들을 하나의 문서로 묶습니다(`grouping.py`).

## 3. 실행 방법

```bash
pip install -r requirements.txt
cp .env.example .env   # GROQ_API_KEY, CEREBRAS_API_KEY를 본인 키로 채울 것
cd src

# 정답이 있는 package_01: 정확도/confusion matrix까지 출력
python3 main.py --pdf "../data/01.990145627/01.990145627_shuffled.pdf" \
                --gt "../data/01.990145627/package_01_gt.json"

# 정답이 없는 package_02: 분류 결과만 출력
python3 main.py --pdf "../data/02.990367284_shuffled.pdf"

# 문서 단위 그룹핑 결과
python3 grouping.py "../data/01.990145627/01.990145627_shuffled.pdf"

# 결과표/시각화 PDF 생성
python3 report.py

# 분류 결과를 바탕으로 원본 PDF를 카테고리별 파일로 실제로 쪼개기
python3 split_by_category.py "../data/01.990145627/01.990145627_shuffled.pdf" "../output/package_01_split"
python3 split_by_category.py "../data/02.990367284_shuffled.pdf" "../output/package_02_split"
```

API 키가 없어도 규칙 기반 결과(package_01 기준 38/39, 97.4%)는 그대로
확인 가능합니다. LLM 호출이 필요한 페이지만 실패로 처리됩니다.

## 4. 결과

### 측정 방법

`package_01_gt.json`(섹션 1-2에서 설명한 방식으로 자체 역산한 정답)과
파이프라인 예측 결과를 페이지 번호 기준으로 1:1 비교해 정확도를 계산합니다
(`evaluate.py`의 `evaluate()`). 계산식은 `맞은 페이지 수 / 전체 페이지 수`이며,
카테고리별 오분류 양상은 confusion matrix(행=정답, 열=예측)로 함께
산출합니다. 실행 방법: `python3 main.py --pdf <경로> --gt <GT json 경로>`.

### package_01 (정답 있음)

- 정확도: **38/39 (97.4%)**
- 규칙 기반으로 38페이지, LLM은 정확히 1페이지(8번)만 호출
- Confusion Matrix, 페이지별 상세 결과: `classification_report.pdf` 참고

### package_02 (정답 없음, 44페이지)

- 분류 결과: `classification_report.pdf` 참고
- LLM 폴백이 10페이지에서 호출됨 (package_01은 1페이지) — package_02가
  package_01보다 규칙 패턴과 어긋나는 페이지가 많다는 뜻이며, 특히
  `INCOME_DOC` 패턴이 표본 1개로 만들어진 한계가 실제로 드러났을 가능성이
  있습니다.
- `OTHER`로 분류된 페이지: 11, 26, 40번 — 정답이 없어 진짜 미분류 대상
  문서인지, 또 다른 텍스트 추출 문제인지 확정하지 못했습니다. 후속 확인이
  필요합니다.

## 5. 오답 분석

| 페이지 | 정답 | 예측 | 원인 |
|---|---|---|---|
| package_01 8번 | TITLE_REPORT | OTHER | 반전 + 글자 이중 렌더링이 겹친 페이지. `text[::-1]`로 반전은 복원 가능하지만 이중 렌더링은 복원 불가(예: `sample`이 `ssaammppllee`로 남음). 규칙과 LLM 모두 실패 — 근본 원인이 텍스트 추출 실패이지 분류 로직의 한계가 아님을 확인. |

package_01에서 검증 과정 중 확인된 것: 자동 유사도 매칭으로 GT를 만들 때
17번 페이지가 `TITLE_REPORT`로 잘못 매칭되었던 것을 수동 검증(원문 대조)으로
발견해 `CREDIT_REPORT`(신용점수 disclosure)로 직접 수정했습니다. 이는
"자동 매칭 점수가 낮으면(0.5 미만) 반드시 원문을 재확인해야 한다"는
근거가 되었습니다.

## 6. 한계

- **반전 감지 휴리스틱은 100% 정확하지 않습니다.** 글자 중복 렌더링이
  겹친 경우 복원 불가.
- **GT 자체가 파생 데이터입니다.** 사람이 라벨링한 공식 정답이 아니라,
  원본 문서와의 텍스트 유사도 매칭 + 저신뢰 구간 수동 검증으로 만든
  근사치입니다 (39개 중 23개는 유사도 0.9 이상 고신뢰, 15개는 저신뢰
  구간이라 수동 검증, 그중 1개 오류 수정).
- **INCOME_DOC 카테고리는 표본이 1페이지뿐입니다.** 과제 스펙상 이 카테고리는
  Paystub, W-2, 1040, 1099, VOE 등 다양한 형태를 포괄해야 하지만, 실제
  확보한 예시는 부동산 중개인의 손익 정산서 1건뿐이라 패턴이 다른 형태의
  소득증빙에는 전혀 맞지 않을 가능성이 높습니다. package_02에서 LLM 폴백
  빈도가 늘어난 것이 이 한계와 관련 있을 수 있습니다.
- **그룹핑 결과가 두 패키지 모두 전부 1페이지짜리 그룹으로만 나옵니다.**
  코드 결함이 아니라, 제공된 두 shuffled 파일이 문서 블록 단위가 아니라
  페이지 단위로 완전히 랜덤 셔플되어 있어(인접 페이지가 같은 카테고리인
  경우가 0건) 생기는 현상입니다. 그룹핑 로직 자체는 합성(fake) 데이터로
  다중 페이지 그룹 정상 동작을 별도 검증했습니다.
- **few-shot 예시를 아직 채우지 않았습니다.** `llm_classifier.py`의
  `FEW_SHOT_EXAMPLES`는 현재 비어있어 LLM은 순수 zero-shot(카테고리 설명만
  제공)으로 동작합니다.

## 7. 다음 단계 (실무 확장을 고려한다면)

- **문서 유형 추가**: `config.py`의 `KEYWORD_PATTERNS`와 `CATEGORIES`에
  새 카테고리만 추가하면 되는 구조라 확장이 용이합니다.
- **대량 처리**: 현재는 PDF 1개를 순차 처리하는 구조입니다. 여러 패키지를
  동시에 처리하려면 페이지별 LLM 호출을 비동기/배치로 묶어 처리량을
  올릴 수 있습니다.
- **데이터 추출 단계 연결**: 분류+그룹핑 이후, 문서 유형별로 특화된 필드
  추출(예: URLA에서 대출 금액, Credit Report에서 신용점수)을 다음 단계로
  이어붙일 수 있는 구조입니다 (그룹핑 결과가 `start_page`/`end_page`를
  가지고 있어 문서 단위 후처리에 바로 활용 가능).
- **반전 감지를 `/Rotate` 메타데이터 기반으로 결정적으로 전환**: 지금은
  단어 매칭 개수 기반 휴리스틱인데, `pypdf`/`pdfplumber`로 각 페이지의
  `/Rotate` 값을 직접 읽어 180도 페이지만 결정적으로 복원하는 방식이
  휴리스틱보다 더 정확하고 예측 가능할 것으로 예상합니다. 90/270도
  페이지의 단어 순서 뒤섞임 문제까지 근본적으로 해결하려면, 문자 좌표
