# MK Lending 대출서류 분류기

여러 종류의 대출 서류가 무작위로 섞인 PDF 패키지를 페이지 단위로 분류하고,
연속된 페이지를 문서 단위로 그룹핑하는 프로젝트입니다.

## 1. 실행 방법

```bash
pip install -r requirements.txt
cp .env.example .env   # GROQ_API_KEY, CEREBRAS_API_KEY를 본인 키로 채울 것
cd src

# 정답이 있는 package_01: 정확도/confusion matrix까지 출력
python3 main.py --pdf "../data/01.990145627/01.990145627_shuffled.pdf" \
                --gt "../data/01.990145627/package_01_gt.json"

# 정답이 없는 package_02: 분류 결과만 출력
python3 main.py --pdf "../data/02.990367284_shuffled.pdf"

# 문서 단위 그룹핑 결과
python3 grouping.py "../data/01.990145627/01.990145627_shuffled.pdf"

# 결과표/시각화 PDF 생성
python3 report.py

# 분류 결과를 바탕으로 원본 PDF를 카테고리별 파일로 실제로 쪼개기
python3 split_by_category.py "../data/01.990145627/01.990145627_shuffled.pdf" "../output/package_01_split"
python3 split_by_category.py "../data/02.990367284_shuffled.pdf" "../output/package_02_split"
```

필요 환경: Python 3.12 기준으로 개발/테스트했습니다. API 키가 없어도
규칙 기반 결과(package_01 기준 38/39, 97.4%)는 그대로 확인 가능하며,
LLM 호출이 필요한 페이지만 실패로 처리됩니다.

## 2. 사용한 기술 스택과 선택 이유

- **pdfplumber**: PDF 페이지별 텍스트 추출. 텍스트 레이어가 있는 PDF임을
  확인(`char_count=0`인 페이지 0개)하고 별도 OCR 없이 진행했습니다.
- **정규식(regex) 기반 1차 분류**: 이 문서들은 표준 양식이라 특정 문구가
  페이지마다 매우 규칙적으로 반복됩니다. 정규식은 LLM보다 빠르고, 무료이고,
  결과가 결정적(deterministic)입니다. package_01 기준 순수 규칙만으로
  38/39(97.4%) 정확도가 나와, 표준 양식 분류에는 규칙 기반이 충분히
  효과적임을 확인했습니다.
- **LLM 폴백 (상용 API: Groq `llama-3.3-70b-versatile` 1순위 →
  Cerebras `llama3.3-70b` 2순위)**: 규칙이 하나도 매칭하지 못한 페이지만
  LLM으로 재분류합니다. 표준 양식 문서에 매 페이지마다 LLM을 호출하는
  것은 비용/속도 면에서 비효율적이고 재현성도 떨어지지만, 규칙만으로는
  데이터가 달라지면(다른 대출 건, 다른 서식) 일반화가 어렵습니다. 두
  방식의 장점만 취하기 위해 하이브리드로 설계했습니다. LLM 호출 기준은
  "정규식 매칭이 1개 이하"로 시작했으나, 매칭 1개(`XACTUS`처럼 특이적인
  고유명사)로 이미 정확했던 페이지까지 LLM이 뒤집는 역효과를 확인하고
  "매칭 0개(규칙이 정말 아무 단서도 못 찾은 경우)"로 기준을 좁혔습니다.
- **pypdf**: 분류 결과를 바탕으로 원본 PDF를 카테고리별 파일로 실제
  분리(splitting)하는 데 사용. 원본 페이지의 `/Rotate` 메타데이터를
  0도로 정규화해 산출물이 화면에 똑바로 보이도록 처리했습니다.
- **matplotlib**: 별도 리포트 라이브러리 없이 confusion matrix 히트맵과
  페이지별 결과표를 PDF로 출력하는 데 사용했습니다.

## 3. 문제 해결 접근 방식 및 처리 흐름

1. **먼저 실제 데이터를 눈으로 본다.** 정규식을 짜기 전에 PDF 39페이지
   텍스트를 뽑아 직접 읽으며 카테고리별 반복 패턴을 찾았습니다.
2. **정답(GT) 없이는 아무것도 검증할 수 없다.** `package_01_gt.json`이
   별도 파일로 제공되지 않아, 함께 제공된 섞이기 전 원본 4개 문서
   (URLA/Credit Report/Income P&L/Title Report)와 shuffled 페이지를
   텍스트 유사도로 대조해 GT를 직접 역산했습니다. 자동 매칭 점수가
   낮은 페이지는 원문을 직접 대조해 수동으로 재검증했습니다.
3. **규칙(정규식)만으로 얼마나 되는지 먼저 측정한다.** LLM 없이 순수
   키워드 매칭으로 베이스라인을 잡았습니다.
4. **규칙이 실패하는 지점만 정밀하게 LLM으로 보완한다.** 전체를 LLM에
   맡기지 않고, 규칙이 못 잡는 페이지만 골라서 넘겼습니다.
5. **분류 결과를 문서 단위로 그룹핑한다.** 연속된 페이지 중 카테고리가
   같은 것들을 하나의 문서로 묶고 시작/끝 페이지를 식별합니다.
6. **정확도/오답을 측정하고, 실제 파일 산출물까지 만든다.** confusion
   matrix로 오분류 양상을 분석하고, 분류 결과를 실제 PDF 파일로 쪼개
   결과를 눈으로 검증했습니다.

이 순서를 택한 이유는, 규칙 기반부터 시작해야 "LLM이 왜 필요한지"를
데이터로 증명할 수 있고, 반대로 LLM부터 시작하면 규칙으로 충분한 페이지까지
불필요하게 API를 호출하게 되기 때문입니다.

**핵심 발견**: 텍스트 추출 중 일부 페이지가 반전되어 나오는 현상을
발견했는데, 처음엔 병합 과정의 텍스트 인코딩 버그로 추정했습니다. 이후
분류 결과를 실제 PDF로 쪼개 눈으로 검증하는 과정에서, `pypdf`로
`/Rotate` 메타데이터를 확인해 **진짜 원인이 페이지 자체의 회전
(90/180/270도)** 이었음을 특정했습니다(39페이지 중 26페이지에 회전이
걸려 있었음). 180도 회전은 텍스트를 문자 단위로 정확히 반전시켜
추출시켜, `text[::-1]`로 복원 가능했습니다.

## 4. package_01 기준 자체 측정 정확도 (측정 방법 포함)

**측정 방법**: `package_01_gt.json`(위 2번 방식으로 자체 역산한 정답)과
파이프라인 예측 결과를 페이지 번호 기준으로 1:1 비교해 정확도를 계산합니다
(`evaluate.py`의 `evaluate()`). 계산식은 `맞은 페이지 수 / 전체 페이지 수`이며,
카테고리별 오분류 양상은 confusion matrix(행=정답, 열=예측)로 함께
산출합니다. 실행: `python3 main.py --pdf <경로> --gt <GT json 경로>`.

**결과**: **38/39 (97.4%)**. 규칙 기반으로 38페이지, LLM은 정확히
1페이지(8번)만 호출되었습니다. Confusion Matrix와 페이지별 상세 결과는
`classification_report.pdf`에 있습니다.

유일한 오답(8번 페이지)은 회전(270도)과 글자 이중 렌더링 아티팩트가
겹쳐 텍스트 추출 자체가 불가능했던 경우로, 규칙과 LLM 모두 실패했습니다
— 분류 로직의 한계가 아니라 텍스트 추출 실패가 근본 원인임을 확인했습니다.

**package_02**(정답 미제공, 44페이지) 분류 결과는 `classification_report.pdf`
와 `output/package_02_split/`(카테고리별로 실제로 쪼갠 PDF)에 포함했습니다.

## 5. 현재 구현의 한계 및 개선 방향

- **반전 감지 휴리스틱은 100% 정확하지 않습니다.** 지금은 흔한 영어
  단어 매칭 개수 비교로 반전 여부를 판단하는데, `/Rotate` 메타데이터를
  직접 읽어 180도 페이지만 결정적으로 복원하는 방식이 더 정확하고
  예측 가능할 것입니다. 90/270도 페이지의 단어 순서 뒤섞임까지 근본적으로
  해결하려면 문자 좌표 기반으로 읽기 순서를 재정렬하는 로직이 필요합니다.
  글자가 이중으로 겹쳐 찍히는 아티팩트(package_01 8번)는 현재 복원
  불가능합니다.
- **GT 자체가 파생 데이터입니다.** 사람이 라벨링한 공식 정답이 아니라,
  원본 문서와의 텍스트 유사도 매칭 + 저신뢰 구간 수동 검증으로 만든
  근사치입니다.
- **INCOME_DOC 카테고리는 표본이 1페이지뿐입니다.** 과제 스펙상 이
  카테고리는 Paystub, W-2, 1040, 1099, VOE 등 다양한 형태를 포괄해야
  하지만, 실제 확보한 예시는 부동산 중개인의 손익 정산서 1건뿐이라 다른
  형태의 소득증빙에는 패턴이 맞지 않을 가능성이 높습니다. package_02에서
  LLM 폴백 빈도가 package_01보다 훨씬 높았던 것(10페이지 vs 1페이지)이
  이 한계와 관련 있을 수 있습니다.
- **그룹핑 결과가 두 패키지 모두 전부 1페이지짜리 그룹으로만 나옵니다.**
  코드 결함이 아니라, 제공된 두 shuffled 파일이 문서 블록 단위가 아니라
  페이지 단위로 완전히 랜덤 셔플되어 있어(인접 페이지가 같은 카테고리인
  경우가 0건) 생기는 현상입니다. 그룹핑 로직 자체는 합성(fake) 데이터로
  다중 페이지 그룹 정상 동작을 별도 검증했습니다.
- **few-shot 예시를 채우지 않았습니다.** `llm_classifier.py`의
  `FEW_SHOT_EXAMPLES`는 현재 비어있어 LLM은 순수 zero-shot(카테고리
  설명만 제공)으로 동작합니다. 실제 오답 사례를 기반으로 채우면 LLM
  정확도를 더 올릴 수 있을 것으로 예상합니다.
- **package_02의 OTHER 3페이지(11, 26, 40) 원인 미확인**: 정답이 없어
  실제 미분류 대상 문서인지, 또 다른 텍스트 추출 문제인지 확정하지
  못했습니다.

**개선 방향(확장 고려)**

- **문서 유형 추가**: `config.py`의 `KEYWORD_PATTERNS`와 `CATEGORIES`에
  새 카테고리만 추가하면 되는 구조라 확장이 용이합니다.
- **대량 처리**: 현재는 PDF 1개를 순차 처리하는 구조입니다. 여러 패키지를
  동시에 처리하려면 페이지별 LLM 호출을 비동기/배치로 묶어 처리량을
  올릴 수 있습니다.
- **데이터 추출 단계 연결**: 분류+그룹핑 이후, 문서 유형별로 특화된 필드
  추출(예: URLA에서 대출 금액, Credit Report에서 신용점수)을 다음 단계로
  이어붙일 수 있는 구조입니다 (그룹핑 결과가 `start_page`/`end_page`를
  가지고 있어 문서 단위 후처리에 바로 활용 가능).
